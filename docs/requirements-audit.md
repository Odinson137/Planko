# Сверка Planko с перепиской заказчика

Дата: 19 сентября 2026 года. Проверены исходный код, доступная переписка за 12 августа — 10 сентября и автоматические тесты. **Полного соответствия пока нет.** Основной цикл «стена → панели и проёмы → раскрой → ведомость» реализован, но остаются функциональные пробелы и воспроизводимые ошибки.

Обновление 20 сентября: исправлены A2 (диагональные профили) и A3 (индикатор сохранения); A1 оставлен без изменений по решению пользователя. Замечание о каталоге уточнено: это расхождение с первоначальными сообщениями, а не подтверждение окончательно согласованного ассортимента.

Добавление и редактирование панелей и реек всегда сохраняет позицию в общий каталог на этом компьютере, без чекбокса. Общий каталог хранится отдельно от проектов. Новые проекты используют его размеры; при открытии существующих проектов добавляются недостающие позиции, а сохранённые размеры остаются прежними. Удаление позиции из проекта не удаляет её из общего каталога и не восстанавливает её при повторном открытии этого проекта. Редактор металлических профилей в это изменение не входит.

Экспорт `.planko.json` включает материалы проекта с размерами, толщинами и декорами вместе с геометрией и настройками. Импорт на другом компьютере сохраняет эти данные внутри нового проекта и не публикует их автоматически в местный общий каталог. При совпадении ID материала проект использует версию из файла. Чтобы сделать импортированную позицию общей, её можно открыть в редакторе каталога и сохранить. Изображения текстур и справочник металлических профилей поставляются с приложением, а не в файле проекта; при переносе между разными версиями приложения их содержимое может отличаться.

Это сверка с требованиями заказчика, а не с обещаниями README. Упомянутые в переписке исходные PDF, фотографии-примеры и документ со скриншотами в приложенном тексте отсутствуют. Поэтому визуальное совпадение отчётов и конкретную ошибку из файла «Окна Виктория» подтвердить нельзя. В этой проверке не проводилась приёмка интерфейса, визуальная проверка экспортированных PDF и установка на другом компьютере.

## Статус замечаний

Статус обновлён 20 сентября 2026 года после уточнений пользователя.

### A1. Удаление применённого проёма оставляет отверстие — принятое ограничение

В `useProjectStore.applyOpening` исходная геометрия заменяется результатом вычитания. `removeOpening` удаляет запись проёма и его стыки, но не восстанавливает панели.

Воспроизведение через store: стена 2000 × 2500, добавить дверь 900 × 2100, применить, удалить. Проёмов становится 0, а площадь отделки остаётся **3,11 м²**. Пользователь 20.09 указал, что это поведение не требует исправления; оно сохранено.

### A2. Обрезка диагонального профиля проёмом — исправлено

Вместо проверки середины линии вычисляются интервалы пересечения всего отрезка с проёмами. Перекрывающиеся вырезы вычитаются один раз; накладные элементы и касание угла не разрывают профиль. Сохраняются направление линии, параметры профиля и связь фрагментов с исходным редактируемым стыком. Диагональные группы больше не превращаются в вертикальные линии при расчёте.

Контрольный пример: стена 2000 × 2000; профиль от (0,0) до (2000,2000); окно (100,100), 400 × 400. Теперь остаются два отрезка общей длиной **2262,74 мм**, и этот метраж используется в спецификации.

### A3. Индикатор несохранённых изменений — исправлено

Store централизованно отмечает изменения стен, проёмов, материалов, каталога, профилей, изгибов и названия проекта. Выбор элемента и открытие редактора сами по себе статус не меняют. Успешное сохранение и загрузка сбрасывают флаг; ошибка сохранения его не сбрасывает. Правки, сделанные во время сохранения, остаются в памяти и требуют следующего сохранения. Надпись «Сохранено!» больше не перекрывает новое несохранённое изменение.

## Исправления, подтверждённые новыми тестами

1. Создание проекта с размерами 5000 × 3200 оставляло исходный полигон 3600 × 2750. Теперь геометрия соответствует введённым размерам.
2. В полигональной модели терялись сведения о радиусных изгибах. Теперь они вычисляются по итоговым границам деталей после вырезов.
3. В режиме общей глубины откосов спецификация читала устаревшие глубины сторон: 400 мм давали 800 мм профиля вместо 1600 мм на четыре стыка окна. Теперь учитывается общий размер.
4. Сводный метраж профилей учитывал участки внутри окон до обрезки. Теперь используются конечные отрезки. Выбранный профиль с нулевым монтажным зазором также попадает в заказ.
5. Количество хлыстов считалось как округление суммарной длины: три отрезка по 1600 мм ошибочно давали два трёхметровых хлыста. Теперь учитывается возможность разместить каждый отрезок целиком; остатки могут использоваться на других стенах.
6. Свободный раскрой листов не оставлял 4 мм между деталями и округлял дробные размеры. Теперь пропил зарезервирован, размеры не округляются перед упаковкой.
7. Размеры деловых остатков не учитывали пропил. Теперь остатки получаются вычитанием занятых областей с пропилом и не перекрываются.
8. При повороте детали на 90° свободная область внутреннего выреза переносилась в неверную позицию. Теперь позиция согласована с преобразованием координат производственного чертежа.

Изменения вычислений могут увеличить закупочное количество листов и профилей в проектах, для которых прежний результат был занижен. Автоматический расчёт всё ещё не гарантирует математически минимальное число заготовок и не заменяет согласование технологии обработки.

Команды проверки:

```sh

npm run build
```

`npm test -- --test-reporter=spec` даёт краткий вывод; `--test-name-pattern=...` позволяет отбирать сценарии. Включены source maps для ссылок ошибок на исходные `.test.ts`. Отдельная проверка типов тестов нужна, поскольку esbuild сам по себе не выявляет неверные типы аргументов.
